# Engineering Workflow Benchmark

## v0.15 Multi-Session benchmark extension

The workflow benchmark now measures not only call count but safe parallel throughput. Two ChatGPT conversations authenticated as the same principal must be able to run independent projects without sharing private process/PT​Y/serial/debug state. Writable sessions use separate worktrees/build directories; exclusive hardware or shared-output project variants reject the second owner with `RESOURCE_BUSY` rather than racing.

A new conversation should resume established work with one `work_session_resume(sessionId)` call returning the bounded Context Capsule, owned runtime resources, recent workflow runs and worktree state. Reconstructing state by replaying the full conversation is explicitly not part of the benchmark.

Node-wide update/restart/rollback operations must observe active workflow interlocks and fail with `NODE_BUSY` instead of interrupting a critical typed workflow. Owner Stop remains available as an explicit recovery action.


This document records the high-signal GitHub projects reviewed before introducing the RWMCP Engineering Workflow Engine.

The goal is not to clone another task runner. The goal is to remove repeated per-chat setup/build/flash/monitor/ROS commands while preserving RWMCP's typed tools, authorization, resource leases, audit trail, and workspace containment.

## Design conclusions

RWMCP adopts these patterns:

1. **Project-local manifest** — recurring project facts live in `.rwmcp/project.yaml`, not in chat history.
2. **Typed workflow registry** — workflows are named semantic operations, not arbitrary shell recipes.
3. **Provider abstraction** — OpenOCD, ESP-IDF, ROS 2 and future providers remain behind constrained adapters.
4. **Environment bootstrap** — ROS distro/workspace setup and similar environment activation are generated by RWMCP instead of repeated manually in every chat.
5. **Hardware identity and leases** — ports/probes are explicit or deterministically resolved and locked during mutation.
6. **Plan before run** — destructive compound workflows can be resolved into concrete steps/defaults without execution.
7. **Fail fast** — a failed build prevents flash; a failed flash prevents monitor.
8. **Structured outputs** — workflow steps return machine-readable status/results for ChatGPT instead of forcing it to parse a long shell transcript.
9. **No arbitrary shell in project manifests** — project profiles store data/defaults only.
10. **Raw shell remains fallback** — new recurring behavior should graduate into a typed adapter or workflow.

## Why not embed a generic Taskfile/Justfile clone?

A generic task runner would reduce typing but would reintroduce the exact risk RWMCP is designed to avoid:

```text
AI -> arbitrary recipe -> shell string -> workstation/hardware
```

The RWMCP direction is instead:

```text
ChatGPT Web
    |
    v
engineering_workflow_run("firmware.build_flash_monitor")
    |
    +--> canonical project profile
    +--> typed firmware adapter
    +--> hardware resource lease
    +--> typed serial adapter
    |
    v
structured workflow result
```

Custom workflows may be added later, but only through a typed step registry with schemas, permission classification, deterministic resource ownership, and bounded execution. A manifest must never become an unreviewed shell execution surface.

## v0.10 foundation

The first workflow engine intentionally starts small:

- `engineering_project_inspect`
- `engineering_profile_init`
- `engineering_workflow_list`
- `engineering_workflow_plan`
- `engineering_workflow_run`

Built-in workflows:

- `firmware.build`
- `firmware.build_flash`
- `firmware.build_flash_monitor`
- `ros2.health`

The next depth should come from recurring real work, not from adding names speculatively:

1. STM32 build/flash/verify/debug/HardFault acceptance.
2. ESP-IDF build/flash/monitor/expect/coredump/OTA acceptance.
3. ROS 2 source/build/launch/graph/TF/QoS/topic-rate/Nav2/diagnostics/bag workflows.
4. FreeRTOS task/stack/watchdog + RTT/SWO diagnostics.
5. Controlled provider/toolchain provisioning.
