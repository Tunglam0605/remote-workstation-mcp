# STM32 E1 authoritative reference review

This record captures source evidence used to shape RWMCP Phase E1. It is not a replacement for vendor documentation.

## Source priority

1. Vendor manuals and specifications.
2. Vendor-maintained repositories and release notes.
3. Upstream tool documentation and release notes.
4. Standards bodies / architecture owners.
5. Community issues and articles only as discovery evidence, never as the authority for safety or CLI semantics.

## Reviewed sources

### STMicroelectronics — STM32CubeMX UM1718

Source:
https://www.st.com/resource/en/user_manual/dm00104712-stm32cubemx-for-stm32-configuration-and-initialization-c-code-generation-stmicroelectronics.pdf

Relevant evidence:
- Saving a CubeMX project persists the user configuration in an `.ioc` file.
- CubeMX project folders are documented as containing one `.ioc` project file.

RWMCP decisions:
- `stm32_ioc_inspect` is read-only and never launches CubeMX or project code.
- Multiple project-root `.ioc` files are treated as ambiguous and require an explicit filename rather than guessing.
- The parser treats the file as bounded project metadata, not as an execution recipe.

### STMicroelectronics — STM32CubeH7 official repository and release notes

Sources:
https://github.com/STMicroelectronics/STM32CubeH7
https://github.com/STMicroelectronics/STM32CubeH7/blob/master/Release_Notes.html

Relevant evidence:
- ST ships CMSIS device content, HAL/LL, BSP and middleware as versioned STM32Cube firmware packages.
- ST notes that GitHub rolling state may be ahead of the package available through st.com / CubeMX.

RWMCP decisions:
- Preserve `ProjectManager.FirmwarePackage` evidence from `.ioc` metadata instead of assuming the latest upstream package.
- Environment/tooling decisions should be tied to the project-declared package when available.
- Vendor repositories are useful references, but branch head is not automatically the correct production baseline for an existing firmware project.

### OpenOCD — Debug Adapter Configuration

Source:
https://openocd.org/doc/html/Debug-Adapter-Configuration.html

Relevant evidence:
- The modern `st-link` driver supports ST-LINK/V2, STLINK-V3 and STLINK-V3PWR.
- The older HLA-based ST-LINK API is deprecated.

RWMCP decisions:
- Keep the current `interface/stlink.cfg` + SWD path.
- Do not regress to `interface/stlink-hla.cfg` / HLA unless a specifically justified compatibility case is introduced.
- Continue keeping OpenOCD argv generated by typed adapters rather than exposing arbitrary TCL.

### Arm — CMSIS 6 official repository and releases

Sources:
https://github.com/ARM-software/CMSIS_6
https://github.com/ARM-software/CMSIS_6/releases

Relevant evidence:
- CMSIS Core and device abstractions are maintained and versioned upstream by Arm.
- Stable tagged releases are the production reference; repository `main` is explicitly development state.

RWMCP decisions:
- Cortex-M fault/register decoding should remain aligned to CMSIS/architecture-defined registers.
- Future fault/debug enhancements should reference stable CMSIS releases or architecture documentation rather than ad-hoc register tables.

### Keil — µVision command-line documentation

Sources:
https://www.keil.com/support/man/docs/uv4/uv4_commandline.asp
https://www.keil.com/support/man/docs/uv4cl/uv4cl_commandline.htm

Relevant evidence:
- `UV4 -b <project>` is the documented batch build path.
- `-t` selects an explicit target.
- `-o` selects build log output.
- Documented ERRORLEVEL values distinguish clean build, warnings, errors and fatal errors.

RWMCP decisions:
- Keep Keil as a constrained typed provider using explicit project + target + log output.
- Preserve structured exit-code interpretation and parsed diagnostics.
- Do not expose arbitrary µVision command strings through project profiles or MCP tools.

## Limits of the current IOC parser

The reviewed ST documentation establishes the role of the `.ioc` file but does not make every internal key a public compatibility contract. Therefore:

- parsing remains bounded and read-only;
- unknown keys are ignored;
- declared pin/peripheral counts are checked and mismatches are surfaced as warnings;
- no source mutation or regeneration is inferred from metadata;
- real-project acceptance files are used alongside synthetic regression tests;
- future CubeMX format changes must be validated against current vendor documentation and real files before broadening the parser.

## Phase-E rule

Every new domain-depth capability should add or update a record like this when authoritative external material changes a design decision.
