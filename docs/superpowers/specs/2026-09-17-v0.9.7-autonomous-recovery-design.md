# v0.9.7 Autonomous Recovery Supervisor Design

## Goal

Make the Windows managed node self-recover without LAN SSH, user clicks, or an external helper whenever the owner intends the OpenAI runtime to be running.

## Invariant

The persistent Control Center is the recovery authority. MCP runtime, tunnel-client, restart/update workers, and WebUI children may fail independently; the Control Center host must remain alive and restore the desired runtime state unless the owner explicitly requested Stop.

## Persistent desired state

Store `%LOCALAPPDATA%\RemoteWorkstationMCP\runtime\desired-state.json` with schema version 1:

```json
{
  "version": 1,
  "desiredRunning": true,
  "mode": "OpenAI",
  "reason": "user-start",
  "maintenanceUntil": null,
  "updatedAt": "2026-09-17T00:00:00.000Z"
}
```

`desiredRunning=false` is written only for an explicit owner Stop. Start, StartOpenAI, Boot and Restart set it true. Update, rollback and Boot use a bounded maintenance window while intentionally stopping/switching the runtime; if the transaction dies, the window expires and autonomous recovery resumes.

## Recovery loop

`control-center-host-windows.ps1` owns a recovery loop alongside its existing WebUI child watchdog. Every five seconds it reads desired state and runtime state.

- If desiredRunning is false: take no recovery action.
- If maintenanceUntil is in the future: take no recovery action.
- If desiredRunning is true and the runtime supervisor is absent: launch stable `bin\rwmcp.ps1 -Action StartOpenAI` without waiting.
- If the supervisor exists but MCP `/healthz` remains unhealthy for at least 15 seconds: launch stable `Restart` handoff.
- If OpenAI mode remains non-ONLINE/stale beyond 90 seconds while MCP health is good: launch stable `Restart` handoff.
- Recovery attempts use 2, 4, 8, 15, 30, 60 second bounded backoff and reset after sustained healthy state.
- Only one recovery action may be in flight at a time.

The recovery loop never depends on SSH, Tailscale, LAN reachability, ChatGPT connectivity, or the WebUI child process.

## Planned maintenance

Boot/update/rollback establish a maintenanceUntil deadline before stopping or switching runtime state. Normal completion clears maintenance by starting the runtime successfully. A crashed worker cannot leave the node permanently offline because the persistent Control Center outlives the worker and resumes recovery after the deadline.

## Safety

- Manual Stop must suppress automatic recovery persistently.
- Recovery uses only the stable launcher and current managed slot; no arbitrary commands or shell strings are accepted from remote callers.
- Foreign ownership of 8684 remains fail-closed.
- Existing update/restart transaction and rollback protections remain authoritative.

## Acceptance

On a real Windows node, without using SSH for recovery:

1. Kill WebUI child -> 8684 returns automatically.
2. Kill tunnel-client -> authenticated ChatGPT path returns automatically.
3. Kill runtime supervisor -> MCP + tunnel return automatically.
4. Interrupt restart worker after runtime stop -> desired-state supervisor restores runtime after bounded maintenance/recovery delay.
5. Restart through Control Center -> runtime PID changes, 8684 host PID stays unchanged, tunnel returns automatically.
6. Update -> new slot activates and tunnel reconnects automatically.
7. Manual Stop -> runtime remains stopped for at least 90 seconds.

Any required SSH/manual Start makes the acceptance fail.
