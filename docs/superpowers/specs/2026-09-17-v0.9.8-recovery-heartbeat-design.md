# v0.9.8 Recovery Supervisor Heartbeat Design

## Goal
Prevent a hung-but-still-running autonomous recovery worker from silently disabling Windows self-recovery.

## Design
The autonomous recovery worker writes `runtime/recovery-supervisor-state.json` atomically after every evaluation. The state contains worker PID, evaluation result, optional error, and `updatedAt` heartbeat timestamp. The persistent Control Center host watches this heartbeat independently of process liveness.

The Control Center gives the worker a 15-second startup grace. After that, a missing or older-than-30-second heartbeat is treated as a hung recovery worker. The host terminates that child and uses its existing bounded restart backoff to launch a fresh recovery worker.

## Invariants
- Control Center remains independent of MCP/tunnel/recovery-worker lifecycle.
- A live PID without a fresh heartbeat is not considered healthy.
- Explicit owner Stop semantics remain unchanged.
- Recovery heartbeat state is non-secret and lives outside version slots.
- SSH is not part of normal recovery acceptance.

## Acceptance
- Static contract test proves heartbeat write/read and stale-worker recycle logic exists.
- Windows integration test proves a fake recovery worker that stops heartbeating is replaced automatically.
- Full Linux/Windows CI, package smoke, and plugin validation pass.
- Real Windows node recovers from WebUI child, tunnel-client, and runtime supervisor failures without SSH/manual rescue.
